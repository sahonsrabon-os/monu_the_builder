মূল সিদ্ধান্ত

সুপারিশ: এখনই runtime swap নয়। প্রথমে P0 security/contract gaps মেটান, তারপর compatibility adapter ও route-level differential tests দিয়ে ধাপে migration করুন।

নিরপেক্ষ প্রকৌশল মন্তব্য

প্রথমে যাচাইযোগ্য ঝুঁকি, তারপর architecture ও verification-এর মূল্যায়ন।

P0 · Security

Requested model allowlist enforce হয় না

src/providers/registry.js-এর resolveModel(id, requestedModel) non-empty requested name-কে সরাসরি ফেরত দেয়; provider-এর registered models তালিকার সঙ্গে membership check নেই। অথচ docs/07-api-contracts.md allowlist check দাবি করে। ফল: authenticated client configured provider-এ unregistered model নাম পাঠাতে পারে; provider billing/access boundary ও documented contract-এর সঙ্গে অমিল। Test suite-এ unknown model rejection test নেই।

P0 · Routing

Default provider fallback-এ hardcoded public URL

src/providers/registry.js-এ OLLAMA_BASE_URL না থাকলে একটি নির্দিষ্ট ngrok URL fallback হয়। “Local-first” নাম/ডকুমেন্টেশনের সঙ্গে public tunnel fallback মেলে না। `.env`/deployment config অনুপস্থিত থাকলে request ভুল বা অননুমোদিত endpoint-এ যেতে পারে। Default-এ endpoint না থাকলে fail-closed হওয়া বা explicit configuration বাধ্যতামূলক করা উচিত।

P1 · Contract

Chat compatibility এবং guarded execution এক নয়

Modular /v1/chat/completions provider-এ সরাসরি chat করে; goal/consent/tool loop আলাদা /v1/execution/run path-এ। এটি ইচ্ছাকৃত separation হতে পারে, কিন্তু generic client যদি chat route দিয়ে tool/agent execution আশা করে, ফল হবে feature mismatch। দুই contract স্পষ্টভাবে প্রকাশ ও test করা দরকার।

P1 · Docs

API contract ও implemented route prefix মেলে না

docs/07-api-contracts.md session routes হিসেবে /api/sessions লেখে; বর্তমান modular server routes /v1/sessions। Phase 12 provider doc streaming না থাকার কথা বলে, কিন্তু Phase 20 SSE test verified বলে। Phase chronology রাখা ঠিক, তবে current contract index-এ কোন phase superseded তা পরিষ্কার হওয়া দরকার।

P2 · Maintainability

Feature count বেশি, integration boundary এখনো আলাদা

Evidence boundary: Extensions suite 59/59 পাস। এটি source-level contract tests-এর evidence; real provider/MCP/TLS/load/parity প্রমাণ নয়। Documentation-এও live Ollama/provider DNS, remote MCP, HTTPS handshake ও WebSocket সীমা উল্লেখ আছে।

Extensions থেকে root-এ নেওয়ার যৌক্তিক candidate

  • Application-scoped permission/ownership pattern, যদি deployment-এ পৃথক application দরকার হয়.

  • Provider adapter/normalizer boundary—বর্তমান provider breadth বজায় রেখে.

Legacy API থেকে Extensions-এ parity candidate

  • Domain/identity/config routes, existing admin dashboard এবং model-list/normalize endpoints.
  • Mission, unified input, agent router, SSOT generation, syllabus/memory write/archive.
  • Current MCP client protocols, WebSocket behavior, usage/stats and startup hooks.
  • All route response/error shapes, DB schema migrations, user/session compatibility.
  • Only routes confirmed in client telemetry/product requirements; unused legacy behavior can be explicitly retired.

কী যুক্ত করা উচিত, কোন ক্রমে

Feature-count নয়, risk ও migration dependency অনুযায়ী।

01 · BEFORE INTEGRATION

Close P0 contract/security gaps

Model must be in the selected provider's discovered/approved catalog; remove public tunnel default; test app ownership and consent bypass rules; document chat vs execution route.

02 · COMPATIBILITY GATE

Build route parity evidence

Capture real clients' used routes, payloads and status/errors. Add differential tests against both runtimes for health, models, admin, chat/stream, MCP, mission and workspace flows.

03 · CONTROLLED CUTOVER

Migrate data and traffic gradually

Define user↔application/session mapping, backup and rollback; run shadow/read-only comparison first; switch a small client cohort; retain legacy fallback until error and usage thresholds hold.

দুটো একত্রে নিলে সম্ভাব্য ফল

  • সঠিকভাবে staged migration: legacy client breadth + modular policy boundaries; maintainability ও safety বাড়তে পারে.
  • দ্রুত full swap: dashboard/domain/workspace/MCP/WebSocket/client flows ভাঙতে পারে; session/auth/model data migration risk.
  • দুই runtime parallel চালালে: provider config, DB state, auth ও routing-এর দুটি source of truth তৈরি হবে; পরিষ্কার ownership ছাড়া drift বাড়বে.

যে দাবিগুলো এখন করা যাবে না

  • “Extensions legacy API-র replacement” — parity inventory তা সমর্থন করে না.
  • “59 tests মানে production-ready” — live provider/MCP/TLS/load evidence নেই.
  • “api.js কেবল পুরোনো বলে বাদ” — root-এ বহু বাস্তব client-facing route ও behavior আছে.
  • “api.js production-safe” — attached logs-এ chat 500 ও double-response crash দেখা গেছে.
